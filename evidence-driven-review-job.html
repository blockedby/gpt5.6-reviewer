Future operating contract / evidence-driven code review

The reviewer’s next job.

Given a completed change, independently decide whether it is ready. Block only on serious defects that are both caused by the change and supported by evidence.

read-only reviewer signal over volume initial + closure modes machine-readable result
01

The mission in one sentence

The reviewer is a decision gate, not a second implementation owner and not a general-purpose repository auditor.

Ready?

A change is ready when no sufficiently important, sufficiently supported defects remain.

Readiness does not come from completing a fixed number of review rounds. It comes from resolving every confirmed blocker. Smaller confirmed issues can be recorded as follow-ups; speculative concerns disappear from the final report.

02

The handoff loop

Responsibility stays explicit: the owner implements, the reviewer judges, and a narrow verifier is used only when one serious claim remains uncertain.

03

What the reviewer actually does

The job is bounded before inspection starts, then each candidate must earn its place in the final output.

A / INPUT

Establish the target

  • Mode: initial or closure
  • Task intent and acceptance criteria
  • Base and head product identities
  • Reviewed diff or changed paths
  • Authorized and forbidden checks
B / INSPECT

Look only where behavior can change

  • Changed code and requested behavior
  • Direct callers, dependencies and invariants
  • Applicable repository instructions
  • Existing relevant tests and artifacts
C / REJECT

Keep noise out

  • Style, taste and optional refactors
  • Generic hardening without a reachable failure
  • Unrelated pre-existing issues
  • Missing tests without a demonstrated behavior gap
  • Documentation polish and process narration
04

The blocking gate

Impact and confidence are separate. A disastrous possibility is not a blocker until evidence makes its existence sufficiently certain.

BLOCK when all are true:

confidence ≥ 80
impact ≥ 3
relationship ∈ {
  introduced,
  regression,
  materially_worsened
}
verification ∈ {
  verified,
  not_required
}
Impact 4 covers security, privacy, data loss, destructive effects and systemic failure. Impact 3 covers broken requirements, primary paths and serious operational failure.
BLOCK Confirmed serious defect caused, regressed or materially worsened by this change.
FOLLOW_UP Confirmed impact-2 issue; serious confirmed pre-existing/unrelated issue; or an important serious check that remains unproven because authorized evidence is missing.
OMIT Impact 1, confidence below 50, disproved claim, ordinary unproven concern, unsupported suggestion or generic improvement.

When to spawn a verifier

impact ≥ 3, 50 ≤ confidence < 80, and a safe check could materially change the verdict.

Scope: one claim, affected locations, one requirement, minimal context.

→

The verifier tries to disprove

VERIFIED
DISPROVED
UNPROVEN

It does not review the rest of the change or discover new issues.

05

Two modes, two scopes

Closure is deliberately smaller than initial review. A fix does not reopen the entire repository for discovery.

INITIAL

Does the requested change work?

  1. Read the task and acceptance criteria.
  2. Inspect changed code and changed behavior.
  3. Trace directly affected callers, dependencies, state and invariants.
  4. Check repository rules and relevant existing tests.
  5. Return only supported blockers and concrete follow-ups.

Not a general audit of unrelated code.

CLOSURE

Did remediation close the named blockers?

  1. Evaluate each prior blocker by stable REV-… ID.
  2. Inspect the remediation diff.
  3. Inspect direct dependencies and invariants touched by the fix.
  4. Look for regressions caused by remediation.
  5. Prefer the original proof: the test now passes or the unsafe path is impossible.

Not a fresh broad review because the head changed.

06

Use the cheapest sufficient proof

Every blocker tells the same causal story: scenario → expected behavior → actual behavior → evidence.

  1. Static proof from reachable codecheapest
  2. Existing failing test, log, trace or runtime artifactreuse evidence
  3. Focused regression testretain if stable
  4. Focused contract testtest the boundary
  5. Safe local reproducerconcrete failure
  6. Integration checkwhen needed
  7. Already-authorized runtime verificationlast resort

Good proof

Natural, deterministic, safe, reasonably cheap, and tied to a stable invariant. A useful test fails before the fix for the claimed reason and passes after correction.

Outside the job

Do not deploy, mutate production, run destructive cleanup, perform real migrations or build expensive images solely to prove a review hypothesis.

07

One complete future job

The archive’s worked example shows the intended lifecycle, from a race-condition blocker to evidence-backed closure.

01 / HANDOFF Prebuild and import exact images

The task requires validation and import to use the same immutable archive.

02 / PROOF A substitution test exposes a race

Validation reads one file; Docker can reopen different bytes at the same path.

03 / VERDICT REV-001 blocks at 98% confidence

Impact 4, introduced, verified by a focused contract test: NOT_READY.

04 / FIX The owner uses one open descriptor

The validated file object is passed to Docker; the pathname is not reopened.

05 / CLOSURE Original proof now passes

REV-001 is fixed; no remediation regression remains: READY.

08

The output and finish line

The reviewer returns compact JSON. Schemas define its shape; a Python policy checker validates disposition and verdict logic.

NOT_READY At least one finding has disposition BLOCK.
READY_WITH_FOLLOW_UPS No blockers remain, but at least one concrete follow-up remains.
READY Neither blockers nor follow-ups remain.

Stop when the evidence says the change is ready—not when the calendar says another review round has happened.

09

Final implementation details

The package is prompt-and-policy infrastructure. Integrate the role files into the agent harness, pass a bounded review request, validate the JSON result, and route only confirmed blockers back to the owner.

Install these responsibilities

  • AGENTS.mdRoutes completed implementation into initial review and remediation into closure review.
  • agents/code-reviewer.mdDefines the independent, read-only reviewer role.
  • skills/code-review/SKILL.mdCanonical scope, evidence, confidence, impact and readiness policy.
  • skills/code-review/verifier-prompt.mdLoaded only for one uncertain serious candidate.
  • schemas/*.jsonDefines machine-readable findings, closure states and verdicts.
  • scripts/review_policy.pyChecks final disposition and verdict consistency using Python 3.10+ standard library.

Required invocation payload

mode: initial | closure
task: requested behavior + acceptance criteria
base_sha: commit before reviewed work
head_sha: current product commit
changed_paths: optional bounded path set
authorized_checks:
  - safe checks the reviewer may run
forbidden_operations:
  - deploys
  - destructive actions
  - production writes

# closure mode also receives:
prior_findings:
  - id: REV-001
    closure_condition: exact proof of closure
remediation_diff: bounded fix diff
  1. Invoke initial reviewProvide task, requirements, product SHAs, changed paths and check boundaries after substantial implementation.
  2. Validate the resultRequire JSON matching review-result.schema.json and reject policy-inconsistent findings or verdicts.
  3. Route by verdictOn NOT_READY, send only BLOCK findings to the implementation owner. Keep follow-ups out of the remediation loop.
  4. Close narrowlyInvoke closure with original blocker IDs and remediation diff. Finish on READY or READY_WITH_FOLLOW_UPS.

Validate review artifacts

python scripts/review_policy.py \
  examples/initial-review-output.json

python scripts/review_policy.py \
  examples/closure-review-output.json

Run policy regression tests

python -m unittest discover \
  -s tests -v
